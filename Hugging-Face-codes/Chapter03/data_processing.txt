3. Why do we need preprocessing?

The model can't understand:

"I love cricket"

directly.

We need:

Text
 ↓
Tokenizer
 ↓
Token IDs
 ↓
Tensor
 ↓
Model

For the MRPC task, we have two sentences, so we need to tell BERT that they form one pair.


4. Tokenizing two sentences together ⭐

This is important:

inputs = tokenizer(
    "This is the first sentence.",
    "This is the second one."
)

BERT turns this into something like:

[CLS] sentence1 [SEP] sentence2 [SEP]

And gives:

input_ids
token_type_ids
attention_mask

What is token_type_ids?

This tells BERT which sentence each token belongs to:

Sentence 1 → 0
Sentence 2 → 1

Example:

[CLS] This is first [SEP] This is second [SEP]
  0    0    0   0    0      1    1    1    1

This is especially relevant to BERT-style sentence-pair inputs. Not every model returns token_type_ids; the tokenizer/model checkpoint determines that.

5. Don't tokenize separately for this task

You might initially think:

tokenizer(sentence1)
tokenizer(sentence2)

But for a sentence-pair classification task, you want:

tokenizer(sentence1, sentence2)

because the model needs to receive them as one paired input.


Why Dataset.map()? ⭐⭐⭐

You could do:

tokenized_dataset = tokenizer(
    raw_datasets["train"]["sentence1"],
    raw_datasets["train"]["sentence2"]
)

But HF recommends using:

dataset.map(...)

because it keeps the result as a Hugging Face Dataset and lets you process the dataset efficiently rather than creating one giant in-memory dictionary.

def tokenize_function(example):
    return tokenizer(
        example["sentence1"],
        example["sentence2"],
        truncation=True
    )

    tokenized_datasets = raw_datasets.map(
    tokenize_function,
    batched=True
)


7. What does batched=True mean?

Without it:

example 1 → tokenize
example 2 → tokenize
example 3 → tokenize
...

With:

batched=True

the tokenizer receives multiple examples at once:

example 1 ┐
example 2 ├→ tokenizer
example 3 ┘

This makes tokenization much faster, because Hugging Face's fast tokenizers are optimized for processing batches

Dataset.map() + batched=True
                ↓
       faster preprocessing



Why DON'T we use padding=True here? ⭐⭐⭐

This is a very important optimization.

Imagine your dataset has sequences:

32 tokens
50 tokens
67 tokens
100 tokens
500 tokens

If you pad everything in the whole dataset to 500:

32  → 500
50  → 500
67  → 500
100 → 500

you're wasting a huge amount of computation on padding.

Instead, HF delays padding until batches are created.

This is called:

Dynamic Padding

Each batch is padded only to the longest sequence inside that batch.


DataCollatorWithPadding ⭐⭐⭐

HF provides:

from transformers import DataCollatorWithPadding

data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

Its job is basically:

Take examples
      ↓
Find longest sequence in THIS batch
      ↓
Pad the other sequences
      ↓
Create tensors

Example batch:

[50 tokens]
[59 tokens]
[47 tokens]
[67 tokens]

Dynamic padding gives:

[67]
[67]
[67]
[67]

instead of padding everything to some huge global maximum.


10. What does the final batch look like?

Suppose we take 8 examples.

Their lengths might be:

50, 59, 47, 67, 59, 50, 62, 32

Maximum = 67

After dynamic padding:

input_ids      → [8, 67]
attention_mask → [8, 67]
token_type_ids → [8, 67]
labels         → [8]

This is exactly the kind of batch your model can consume.

Notice how this connects directly to what you asked me earlier:

input_ids
[B, T]

and after the Transformer:

hidden states
[B, T, C]

Here:

B = 8
T = 67

1. Dataset
   ↓
   raw text + labels

2. Tokenizer
   ↓
   text → input_ids / attention_mask / token_type_ids

3. Sentence pair
   ↓
   tokenizer(sentence1, sentence2)

4. Dataset.map()
   ↓
   apply preprocessing to the whole dataset

5. batched=True
   ↓
   process many examples at once → faster

6. DataCollatorWithPadding
   ↓
   dynamic padding per batch

7. Final batch
   ↓
   input_ids [B,T]
   attention_mask [B,T]
   labels [B]
