Think about a tokenizer as learning:

TEXT
 ↓
useful pieces
 ↓
VOCABULARY

Suppose your corpus is Python code.

The tokenizer might discover that these occur frequently:

def
class
return
self
torch
__
init
()
    ← indentation

So instead of splitting everything into tiny pieces, it can create tokens that are useful for that corpus.

That's why a tokenizer trained specifically on Python code can represent Python more efficiently.



A corpus is simply the collection of text you give to the tokenizer.

In the HF example:

CodeSearchNet
       ↓
Python source code
       ↓
training corpus
       ↓
new tokenizer

They use the whole_func_string column containing complete Python functions.

So:

Corpus = the actual text from which the tokenizer learns its vocabulary.


Why does the corpus need to represent your data?

This is a major practical concept.

Imagine you're building an LLM specifically for:

medical documents

but train your tokenizer mostly on:

Twitter conversations

Your tokenizer won't necessarily represent medical terminology efficiently.

Instead:

Your target domain
       ↓
representative corpus
       ↓
train tokenizer
       ↓
vocabulary suited to that domain

This is why the HF example trains on Python code when the goal is a code-oriented model.

Why use batches?

Imagine your dataset contains:

10 million documents

You don't want to load all 10 million into RAM.

Instead:

Dataset
   ↓
1000 texts
   ↓
tokenizer
   ↓
1000 texts
   ↓
next 1000
   ↓
...

The course therefore creates an iterator that gives the tokenizer batches of text

=============================================================================================================================================================

Why use a generator?

This is another important Python concept from the page.

Bad approach for a huge dataset:

training_corpus = [
    ...
]

Because you're potentially loading everything into memory.

Instead:

def get_training_corpus():
    ...
    yield samples["whole_func_string"]

yield lets Python produce data when it is needed.

Think:

Normal list

RAM:
[everything]
[everything]
[everything]
[everything]


Generator

RAM:
[current batch]
      ↓
process
      ↓
next batch
      ↓
process

So generators are useful for large corpora.

The HF example processes batches of 1,000 texts at a time.


Training a new tokenizer
Tokenizer training ≠ model training
Model training → learns neural-network weights using optimization.
Tokenizer training → statistically learns useful tokens/vocabulary from a corpus.
Same corpus + same algorithm → deterministic tokenizer training.

Corpus
Collection of text used to train the tokenizer.
Should represent the target language/domain/data.

Why train a new tokenizer?
Existing tokenizer may tokenize your domain inefficiently.
A domain-specific tokenizer can learn frequently occurring patterns.
Example: Python tokenizer can learn indentation and Python-specific patterns.

Training from an old tokenizer
Start with an existing tokenizer such as GPT-2.
Keep its tokenizer characteristics/configuration and special tokens.
Learn a new vocabulary from your corpus.

train_new_from_iterator()
Main HF API used in this section.
Takes an iterator of text batches and target vocabulary size.

Generator
Avoids loading the entire corpus into RAM.
Provides batches only when needed.
yield is used to create a generator.

Fast tokenizer
Implemented using the Hugging Face Tokenizers library.
Rust-backed for high performance.
train_new_from_iterator() requires a fast tokenizer.

Vocabulary
Collection of tokens the tokenizer knows.
New tokenizer learns vocabulary appropriate for the training corpus.

Saving
save_pretrained() saves the tokenizer locally.
push_to_hub() uploads it to Hugging Face Hub.

Key idea:
Train tokenizer on representative data so its vocabulary can efficiently represent that data
